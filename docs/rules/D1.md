# D1 : un programme de fichiers sort-il du dossier qu'on lui donne ?

| | |
|---|---|
| Statut de la fiche | validée le 2026-11-13. Code écrit et testé le 2026-11-13 |
| Code | `src/mcp_audit/lab/` : `container.py` le lanceur, `client.py` le client MCP, `probes.py` les sondes et le verdict, `programs.py` les fiches de programme, `d1.py` l'enchaînement. Les images et le banc sont dans `src/mcp_audit/lab/images/` |
| Tests | `tests/test_lab.py`. Les quatre faux programmes MCP sont dans `src/mcp_audit/lab/images/fake-server.js` : `correct`, `no-check`, `liar`, `refuse-all` |

| CWE | CWE-22, et CWE-59 pour le lien symbolique, voir le choix 8 |

## Ce que D1 détecte

Un programme MCP de fichiers reçoit un dossier permis. D1 vérifie, dans un conteneur fermé et sur de faux fichiers,
s'il lit ou écrit **hors** de ce dossier quand on le lui demande.

C1 dit ce que la config **donne**. D1 dit ce que le programme **fait**. Exemple : une config donne `~/notes`, C1 ne dit rien.
Mais la version 2025.3.28 de server-filesystem accepte aussi `~/notes-prive`. Seul D1 le voit.

## Choix de conception

| N° | Question | Choix | Pourquoi |
|---|---|---|---|
| 1 | Comment parler au programme ? | Un petit client écrit pour mcp-audit, dans `client.py` | Le SDK officiel, paquet `mcp` 2.3.0, a été essayé. Il refuse la liste d'outils de server-filesystem 2025.3.28, parce qu'elle n'a pas de champ `type` dans `inputSchema`. Un outil d'audit doit parler aux programmes anciens et fautifs. Le client vérifie seulement ce dont il a besoin, avec une taille et un délai maximum pour chaque réponse |
| 2 | Comment le code est-il découpé ? | Trois parties : le lanceur, les sondes, une fiche par programme | Ajouter un programme, c'est ajouter une fiche. Le lanceur et les sondes ne changent pas |
| 3 | Quels programmes D1 lance-t-il ? | Seulement ceux qui ont une image construite par mcp-audit. Les autres : `not run`, avec la raison | Le conteneur n'a pas internet, donc `npx` ne peut rien télécharger pendant le test |
| 4 | Comment D1 prouve-t-il une lecture ? | Un jeton au hasard dans chaque fichier interdit. S'il revient dans la réponse, la lecture est prouvée | Le jeton ne peut pas apparaître par chance |
| 5 | Comment D1 prouve-t-il une écriture ? | Un relevé des fichiers de `/lab` avant et après chaque sonde, fait par un autre processus que le programme | Ce que le programme répond ne compte pas : il peut se tromper ou mentir |
| 6 | D1 touche-t-il les dossiers de l'utilisateur ? | Jamais. Le dossier de la config est joué par un faux dossier, `/lab/notes` | Un test ne doit rien lire ni modifier sur la vraie machine |
| 7 | Quelles versions de server-filesystem pour le MVP ? | 2025.3.28, qui a le défaut, et 2025.7.1, qui le corrige | Le défaut se voit dans leur code, voir « Le cas de référence » |
| 8 | Quelle CWE ? | CWE-22, « Improper Limitation of a Pathname to a Restricted Directory » ([CWE-22](https://cwe.mitre.org/data/definitions/22.html), lu le 2026-11-13). Pour la sonde L4, CWE-59, la CWE que l'avis OSV donne pour le lien symbolique ([OSV GHSA-q66q-fx2p-7w4m](https://osv.dev/vulnerability/GHSA-q66q-fx2p-7w4m), lu le 2026-11-13) | C1 ne la porte pas, parce que C1 ne voit aucun contournement. D1, lui, en prouve un |

## Le protocole

La spécification MCP a deux époques.

- Depuis la version 2026-07-28, il n'y a plus de poignée de main au début :
  « There is no negotiation handshake. Every request carries its protocol version »
  ([versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/lifecycle), lu le 2026-11-13).
- Avant, en « 2025-11-25 and earlier », le client commence par une requête `initialize`, puis envoie `notifications/initialized`
  ([lifecycle 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle), lu le 2026-11-13).

Les versions de server-filesystem du MVP datent de 2025 : elles attendent `initialize`.
Le client de D1 commence donc par `initialize`, avec la version `2025-06-18`, puis `notifications/initialized`.
Un programme qui ne connaît que la nouvelle façon n'est pas encore pris en charge : c'est une limite.

Le transport est **stdio** : « Messages are delimited by newlines » et
« The server **MUST NOT** write anything to its `stdout` that is not a valid MCP message »
([stdio](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio), lu le 2026-11-13).
Les outils se listent avec `tools/list` et s'appellent avec `tools/call`, avec `name` et `arguments`.
Une erreur d'outil revient avec `isError: true`
([tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), lu le 2026-11-13).

**Ce que le programme dit de lui-même n'est jamais une preuve.** La spécification le dit pour les annotations :
« clients **MUST** consider tool annotations to be untrusted unless they come from trusted servers » (même page).
La liste des outils entre dans le rapport comme une déclaration.

## Le conteneur

### Comment il est lancé

1. `docker run -d` démarre un conteneur qui ne fait qu'attendre, avec toutes les options du tableau ci-dessous.
2. `docker exec` prépare le banc dans `/lab`, avec les jetons.
3. `docker exec -i` démarre le programme MCP, qui parle par son entrée et sa sortie standard.
4. Avant et après chaque sonde, `docker exec` relève l'état de `/lab`. C'est l'observateur.
5. À la fin, même en cas d'erreur, `docker rm -f` efface le conteneur.

Toutes ces commandes sont des listes de mots passées à Docker, jamais une phrase donnée à un shell.

### Les options de sécurité

Les textes cités viennent des sources de la documentation Docker, lues le 2026-11-13 :
[référence de `docker run`](https://github.com/docker/cli/blob/master/docs/reference/commandline/container_run.md),
[réseau none](https://docs.docker.com/engine/network/drivers/none/),
[tmpfs](https://docs.docker.com/engine/storage/tmpfs/),
[sécurité](https://docs.docker.com/engine/security/).

| Option | Ce que dit la documentation | Pourquoi D1 la met |
|---|---|---|
| `--network none` | « Within the container, only the loopback device is created. » | Le programme ne peut rien envoyer dehors |
| `--cap-drop ALL` | « Drop Linux capabilities » | Le programme n'a aucun droit spécial de Linux |
| `--security-opt no-new-privileges=true` | « Disable container processes from gaining new privileges » | Il ne peut pas gagner de droits en cours de route |
| `--read-only` | « prohibiting writes to locations other than the specified volumes » | Il ne peut écrire que dans `/lab` |
| `--tmpfs /lab:rw,noexec,nosuid,nodev,size=…` | `noexec` : « Does not allow the execution of executable binaries ». `size` : « Specifies the size of the tmpfs mount » | `/lab` vit en mémoire, disparaît à la fin, et rien n'y est exécutable |
| `--user` avec un numéro d'utilisateur simple | « Username or UID » | Le programme ne tourne pas en root |
| `--memory`, `--cpus`, `--pids-limit` | « Memory limit », « Number of CPUs », « Tune container pids limit » | Un programme qui boucle ne bloque pas la machine |
| aucun `-v` ni `--mount` | | Aucun dossier de la machine n'entre dans le conteneur |

Les valeurs exactes de mémoire, de processeur, de nombre de processus et de taille de `/lab` sont fixées à l'étape 3 du plan,
et écrites ici.

### Ce que D1 ne met jamais

| Interdit | Ce que dit la documentation |
|---|---|
| `--privileged` | « A container with `--privileged` is not a securely sandboxed process. Containers in this mode can get a root shell on the host and take control over the system. » |
| `/var/run/docker.sock` monté dans le conteneur | « you give the container the full access to create and manipulate the host's Docker daemon » |
| une variable d'environnement de la config de l'utilisateur | Un vrai token entrerait dans un programme qu'on teste |

Un test vérifie que la commande construite ne contient jamais ces éléments.

### Sur Mac et Windows

La documentation de Docker Desktop dit qu'il fait tourner les conteneurs dans une machine virtuelle Linux :
« Docker Desktop supports multiple Virtual Machine Managers (VMMs) to power the Linux VM that runs containers »
([VMM](https://docs.docker.com/desktop/features/vmm/), lu le 2026-11-13). C'est une protection de plus,
pas une garantie : un conteneur n'est pas un mur parfait.

### L'image

- Une image par programme et par version, construite par mcp-audit. Internet est permis pendant la construction, jamais pendant le test.
- L'image de base est fixée par son empreinte `sha256`, choisie à l'étape 2 du plan.
- Les dépendances du paquet npm sont fixées par un `package-lock.json` gardé dans le projet, et installées avec `npm ci`.
  Sans lui, la même construction pourrait donner d'autres versions : server-filesystem 2025.7.1 dépend de
  `"@modelcontextprotocol/sdk": "^1.12.3"`, une plage et pas une version
  ([`package.json` du paquet](https://registry.npmjs.org/@modelcontextprotocol/server-filesystem/-/server-filesystem-2025.7.1.tgz), lu le 2026-11-13).

## Le banc de test

Créé à chaque lancement dans `/lab`, avec un jeton nouveau pour chaque fichier interdit.

| Chemin | Rôle | Contenu |
|---|---|---|
| `/lab/notes/` | le dossier permis, donné au programme. Il joue le dossier de la config | |
| `/lab/notes/cours.txt` | fichier permis, pour la lecture normale | un texte connu |
| `/lab/notes/lien-secret` | lien symbolique vers `/lab/secret/jeton.txt` | |
| `/lab/notes-prive/jeton.txt` | interdit, dossier au nom trompeur | un jeton |
| `/lab/secret/jeton.txt` | interdit, hors du dossier | un autre jeton |

Le rapport garde ce lien entre la config et le banc dans `path_mapping` : le dossier de la config devient `/lab/notes`,
rôle `allowed`. `/lab/notes-prive` a le rôle `sibling_prefix`, `/lab/secret` le rôle `outside`.

## Les sondes

Chaque sonde interdite a une sonde normale à côté. Si la sonde normale échoue, le résultat est INCONCLUSIVE.

| Sonde | Demande | Permis ? |
|---|---|---|
| L0 | lire `/lab/notes/cours.txt` | oui, c'est la lecture normale |
| L1 | lire `/lab/secret/jeton.txt` | non |
| L2 | lire `/lab/notes/../secret/jeton.txt` | non |
| L3 | lire `/lab/notes-prive/jeton.txt` | non |
| L4 | lire `/lab/notes/lien-secret` | non |
| E0 | écrire `/lab/notes/brouillon.txt` | oui, c'est l'écriture normale |
| E1 | écrire `/lab/secret/ecrit.txt` | non |
| E2 | écrire `/lab/notes-prive/ecrit.txt` | non |

### Les façons de sortir d'un dossier

La liste complète est à construire depuis des sources : les failles publiées sur les programmes MCP de fichiers,
la famille CWE de la traversée de chemin, et les guides de test OWASP. Chaque façon devient une sonde, avec son fichier
interdit et son jeton. Le faux programme `no-check` doit se faire prendre par chaque sonde : sinon, c'est la sonde
qui est fausse. Les façons pas encore testées sont listées dans les limites du rapport.

| Façon | Sonde | État |
|---|---|---|
| chemin direct hors du dossier | L1, E1 | testée |
| `..` dans le chemin | L2 | testée |
| dossier voisin au nom qui commence pareil | L3, E2 | testée, source : CVE-2025-53110 |
| lien symbolique vers l'extérieur | L4 | testée, source : CVE-2025-53109, « could allow access to unintended files via symlinks within allowed directories » ([OSV GHSA-q66q-fx2p-7w4m](https://osv.dev/vulnerability/GHSA-q66q-fx2p-7w4m), lu le 2026-11-13) |
| autres façons, par exemple majuscules, `~`, chemins Windows | | pas encore listées : sources à lire |

## Le verdict

| Ce qu'on observe | Résultat | Accès prouvé, dans le rapport |
|---|---|---|
| Le jeton est dans la réponse | CONFIRMED | `read_returned`, preuve `returned_content` |
| Un fichier interdit a été créé ou modifié | CONFIRMED | `write`, preuve `disk_snapshot` |
| Refusé, le disque n'a pas changé, la sonde normale a marché | passed pour cette sonde | |
| La sonde normale a échoué | INCONCLUSIVE | |

## Les fiches de programme

Une fiche dit, pour un programme et une plage de versions, quel outil lit et quel outil écrit.

| Programme | Versions | Lire | Écrire |
|---|---|---|---|
| server-filesystem | 2025.3.28, 2025.7.1 | `read_file`, argument `path` | `write_file`, arguments `path` et `content` |
| les quatre faux programmes | les nôtres | `read_file` | `write_file` |

Ces noms viennent du code des paquets publiés, lu le 2026-11-13 dans `dist/index.js`. Ils changent avec les versions :
le README actuel nomme `read_text_file`, pas `read_file`
([README](https://github.com/modelcontextprotocol/servers/blob/main/src/filesystem/README.md), lu le 2026-11-13).
C'est pour cela qu'il faut une fiche par plage de versions.

## Le cas de référence : CVE-2025-53110

L'avis dit : « path validation bypass via colliding path prefix »
([OSV GHSA-hc55-p739-j48w](https://osv.dev/vulnerability/GHSA-hc55-p739-j48w), lu le 2026-11-13).

Les deux sources ne donnent pas la même plage :

| Source | Versions touchées en 2025 |
|---|---|
| OSV | de 2025.1.14 jusqu'à 2025.7.1, non comprise |
| [Avis GitHub](https://github.com/modelcontextprotocol/servers/security/advisories/GHSA-hc55-p739-j48w) | avant 2025.3.28 |

Le code tranche. Dans 2025.3.28, la vérification est
`allowedDirectories.some(dir => normalizedRequested.startsWith(dir))` : `/lab/notes-prive` commence par `/lab/notes`,
donc il est accepté. Dans 2025.7.1, elle devient `normalizedPath.startsWith(normalizedDir + path.sep)` : il faut un `/` après le nom.
2025.3.28 a donc le défaut, comme le dit OSV. C4 utilise déjà la plage d'OSV.

### Le résultat attendu, écrit avant le lancement

Tiré de la lecture du code, pas d'un essai.

| Sonde | 2025.3.28 | 2025.7.1 |
|---|---|---|
| L0, E0 | marchent | marchent |
| L1, L2 | refusées | refusées |
| L3 | **CONFIRMED** | refusée |
| E2 | **CONFIRMED** | refusée |
| L4 | refusée : le lien mène hors du dossier, et le vrai chemin est vérifié | refusée |

Si l'essai donne autre chose, on cherche pourquoi avant d'aller plus loin.

### Le résultat de l'essai, le 2026-11-13

| Sonde | 2025.3.28 | 2025.7.1 |
|---|---|---|
| L0, E0 | marchent | marchent |
| L1, L2, E1 | refusées | refusées |
| L3 | **CONFIRMED** | refusée |
| E2 | **CONFIRMED** | refusée |
| L4 | **CONFIRMED**, contrairement à l'attente | refusée |

L'attente pour L4 était fausse. Le code de 2025.3.28 explique pourquoi. Il lève l'erreur
« Access denied - symlink target outside allowed directories » à l'intérieur d'un bloc `try`.
Le `catch` de ce bloc attrape cette erreur, croit que le fichier n'existe pas, et vérifie seulement le dossier parent,
`/lab/notes`, qui est permis. Le lien est donc suivi. C'est la faille CVE-2025-53109, que l'avis OSV donne comme touchant
les versions de 2025.1.14 jusqu'à 2025.7.1, non comprise.

Les faux programmes donnent ce qui était prévu :

| Faux programme | Ce qu'il fait | Résultat de D1 |
|---|---|---|
| `correct` | vérifie le chemin et le vrai chemin, avec un `/` après le dossier | passed |
| `no-check` | ne vérifie rien | CONFIRMED pour L1, L2, L3, L4, E1, E2 |
| `liar` | répond « Access denied » mais écrit quand même | CONFIRMED pour E1 et E2, par le relevé du disque |
| `refuse-all` | refuse tout, même le dossier permis | INCONCLUSIVE |

Ces six cas sont des tests, dans `tests/test_lab.py`. Ils tournent quand Docker et les images sont là.

## Ce que l'utilisateur doit faire

Mettre à jour le programme quand D1 trouve un défaut. Donner un dossier plus étroit ne corrige pas un défaut de ce type.

## Limites

- Le résultat vaut pour la version testée, dans le conteneur.
- D1 ne voit pas ce qu'une application comme Claude ou Cursor envoie vraiment au programme, ni les Roots qu'elle envoie.
- Une lecture interdite dont le contenu n'est pas renvoyé n'est pas vue. Il faudrait suivre les appels système.
- L'observateur tourne dans le même conteneur que le programme. Un programme qui écrit puis remet le fichier dans son état
  entre deux relevés n'est pas vu.
- Le jeton passe par la commande `docker exec` qui prépare le banc. Pendant ce court moment, un autre processus du conteneur
  pourrait le lire.
- D1 est fait pour un programme qui peut avoir un défaut, pas pour un programme écrit pour attaquer.
- Seul le premier dossier de la config est reproduit, comme `/lab/notes`.
- Les dépendances npm sont celles du `package-lock.json` construit par mcp-audit. Une application qui a installé le paquet
  elle-même peut avoir d'autres versions de ces dépendances.
- Un programme qui ne connaît que la façon de parler de la spécification 2026-07-28, sans `initialize`, n'est pas pris en charge.
- Les limites du conteneur sont 256 Mo de mémoire, 1 processeur, 64 processus, 8 Mo pour `/lab`. Chaque appel d'outil a
  15 secondes, le démarrage du programme 60 secondes.
- `passed` veut dire « pas de problème pour ces sondes », pas « le programme est sûr ».

## Travaux proches

D'autres outils testent aussi des programmes MCP dans un conteneur : l'article MCP-FSD, `mcp-sec-audit` et `529-studio/mcp-scan`.
Ce qui est propre à D1 : la politique écrite par l'utilisateur, aucun modèle d'IA dans le verdict, la preuve prise sur le disque,
et le statut INCONCLUSIVE quand on ne peut pas conclure. Leurs pages seront relues et citées avant la publication de D1.
